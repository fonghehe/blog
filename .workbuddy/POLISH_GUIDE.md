# 博客语言层润色工作指南（子代理共享）

本文件是润色子代理的执行细则。主代理会在每条任务里指定：语言（lang）、月份目录（dir）、中文源目录（zh_src）。

## 0. 任务本质
这是**语言层面的实质性润色**，不是格式校对。目标是让句子更通顺、措辞更自然、翻译更地道，**但不改变作者想表达的内容（观点/事实/技术结论/经历/历史背景/数据）**。

"保持原意" ≠ "保持原句"：保留意思，不保留别扭的语序、冗余、不自然的措辞、中文直译式英文/日文、简繁转换瑕疵。

## 1. 工作单元
- 处理目录 `dir` 下的**所有 `.md` 文章文件**。
- **必须跳过** `index.md`（VitePress 自动生成的导航页，不是文章）。
- 翻译语言（en/ja/zh-hk/zh-tw）请同时参考 `zh_src` 目录下同名中文文件，用于发现"机械直译 / Chinglish / 中文语序残留"等问题。

## 2. 绝对不能改（STRICT PRESERVE）
- **frontmatter 全部字段**（title/date/tags/categories/等）——一字不改。
- **所有代码**：围栏代码块（```）、行内代码（`...`）、命令行、API 名、配置键、文件路径、URL、GitHub 链接——一字不改。
- **标题层级与 Markdown 结构**（##、列表、表格）。
- **事实、数据、表格、版本号、日期、项目名、人名、历史背景**。
- **不要**用 2026 年的认知改写旧文章。每一年保留当年的技术背景。例如 2018 年的文章里出现了当时不存在的技术（Core Web Vitals、可选链 `?.`、React Hooks、Promise.allSettled 等），**不要修改**——只在汇报里记录疑点。

## 3. 实际要改什么（语言润色）
### 简体中文（zh）
- 语序不顺、冗余、重复、过长句、段落衔接生硬。
- 连接词泛滥（避免 然后/其实/所以/但是/这里 成灾）。
- 技术表达专业但不生硬；口语随意处适当收紧。
- 保留作者个人化、口语化表达，不统一成 AI 腔。

### 英文（en）
- 消除 Chinglish，不要机械保留中文语序。
- 使用技术博客常见的自然英文表达（语法正确 ≠ 地道）。
- 注意时态、冠词、单复数、被动/主动选择。

### 日文（ja）
- 检查助词（は/が/を/に/で 等）是否自然。
- 敬体（です・ます）与常体统一：技术博客正文通常用常体（だ・である），但需与全文一致。
- 符合日本技术社区习惯，目标："日本读者不觉得这是中文翻译"。
- 修正中文直译痕迹，例如：
  - 方案 → アプローチ
  - 痛點/痛点 → 悩みの種 / 課題
  - 出發 → 起点に / 出発点
  - シナリオ → 場面 / ケース
  - 核心的 → 本質的
  - 删除多余的 まず
  - 完全な例 → 全体のサンプル / 完全なサンプル
  - 注意"〜することができます"连用过多、以及"〜ということです"等翻译腔。

### 繁体中文（zh-hk / zh-tw）
- 修正简→繁转换瑕疵（这是繁体文章最大的真实缺陷）：
  - 隻 → 只
  - 機製 → 機制
  - 控製 → 控制
  - 強製 → 強制
  - 限製 → 限制
  - 應用程序 → 應用程式（HK/TW 通用）
  - 用户 → 用戶（HK/TW 通用）
  - 例項 → 實例
  - 箇 → 個
  - 麪試 → 面試
  - 十進製 → 十進制
  - 幹擾 → 干擾
  - 其它常见：里→裡、复→複/復、干→乾/幹（按语境）、云→雲、后→後 等，按语境判断。
- 港台用词差异（HK 偏粵語書面/英式，TW 偏國語）：如 软件→軟體、网络→網路、服务器→伺服器、数据库→資料庫、程序员→程式設計師/軟體工程師，按对应地区习惯。
- 同时仍需做实质性语言润色（不只是改转换瑕疵）。

## 4. 不要做的事（DON'T）
- 不要统一成 AI 风格套话（避免：首先/其次/最后/值得注意的是/综上所述/在当今…/由此可见/不难发现）。
- 不要编造内容：不新增 Benchmark、项目经历，不改事实。
- **不要为了避免改错而不改**——上一轮的问题是过度保守。主动寻找"能看懂但能更好"的地方并修改。
- 不要改动已经自然流畅、无需修改的句子（不为了凑数量强行改）。
- 不要 commit / push / 删除任何文件。

## 5. 执行流程
1. 完整读取每篇文章。
2. 理解作者意图与技术背景（结合年份）。
3. 逐段检查：语序、冗余、重复、长句、连接词、翻译地道度。
4. 修改语言层问题。
5. 重读确认：内容未变、语言更自然。
6. 自检：是否真的改了有语言问题的句子？作者会不会觉得"顺了很多"？是否意外改动了观点（若改了需撤销）？

## 6. Git 操作
- 修改完成后，仅对**实际改动**的文件执行：`git add <绝对路径>`。
- 绝不 `git commit`、绝不 `git push`、绝不删除原文。
- 用 `git diff --cached --stat` 之类确认已暂存。

## 7. 汇报格式（简洁）
请回传：
- 本目录文章总数、实际修改篇数、基本无需修改篇数。
- 3–5 个**实质性句子/措辞优化**的 before→after 例子（展示真正改了语言，而非仅格式）。
- 发现的史实质疑（如旧文时代错置），仅记录不改。
- 繁体文章报告转换瑕疵修正数量。
- 是否某篇确实无需修改而保持原样。
