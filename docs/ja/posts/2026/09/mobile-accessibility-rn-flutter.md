色とアイコンの付いたボタンでも、スクリーンリーダーの利用者には役割が伝わらない場合がある。標準サイズで読める文字も、OS の文字拡大で購入操作を妨げるかもしれない。アクセシビリティは公開直前のラベル修正ではなく機能の受け入れ条件にする。

## 重要な操作から始める

ログイン、検索、送信、エラーからの復旧をたどる。フォーカス順が操作の流れに合い、アイコンボタンに意味のある名前があり、スイッチが状態を読み上げるか確認する。非同期の成功は適切に通知するが、一覧更新のたびに読み上げを中断しない。

RN ではラベル、役割、状態の属性を使い、Flutter では `Semantics` で複合部品を表す。カード全体と内側のボタンを重複して読ませない。

## 文字とレイアウトを同時に試す

文字を拡大しても操作でき、金額と単位が見え、キーボードがエラーを隠さないか確認する。固定高さで文字を切らず、折り返しやスクロールを許す。最後は VoiceOver と TalkBack で実際の操作を完了し、端末と阻害箇所を記録する。

## 「送金確認」の仕事全体で確認する

アクセシビリティの受け入れ確認を実際の仕事に置く。受取人を検索し、確認画面で名前、金額、手数料を確認してから送信する流れだ。見た目で分かれた金額と通貨は、読み上げでは意味のある一つのラベルにする。「続ける」ボタンはアイコン名だけでなく、次の確認段階を伝える。フォームのエラーは項目と結び、送信失敗後はエラー概要か最初の誤りへフォーカスを移す。赤い枠だけでは伝わらない。

React Native では `accessibilityRole`、`accessibilityLabel`、`accessibilityState` と適切なグループ化で意味を表せる。Flutter には `Semantics`、`MergeSemantics`、明示的なフォーカス順がある。ページ全体を一つの読み上げ要素にすると、ボタンを個別に操作できない。非同期読込後やダイアログ開閉時にはフォーカス先を確認し、消えた要素に残さない。文字を大きくしても金額、エラー、主ボタンが見え、固定高さで切らず折り返せるようにする。

| 場面 | 確認する結果 |
| --- | --- |
| 読み上げの順次移動 | 名前、金額、手数料、注意、確認ボタンの順が自然 |
| キーボードやスイッチ | 操作が届き、焦点が見え、ダイアログから抜けられる |
| 拡大文字 | 文が読め、ボタンが重ならず、数字が欠けない |
| 検証失敗 | エラーが読まれ、入力値が残る |

## 自動検査に加えて実機で歩く

まず OS の検査ツールでラベル漏れやコントラストを探し、iOS VoiceOver と Android TalkBack で上の送金操作を最後まで行う。連打、遅い通信中の状態読み上げ、成功後に結果の見出しへ移るフォーカスも試す。スクリーンショットや静的検査だけでは読み上げ順と焦点復帰を証明できない。端末、OS、文字設定、再現手順を記録し、修正後に同じ条件で再確認する。
