報告画面を五つ開くと、ポーリングも五組動く。localStorage にリーダー印を書いても、二つのタブが同時に空を読んでから書けば両方が勝ったと思う。時間切れの引き継ぎには、バックグラウンド停止や端末時計の変化も影響する。

Web Locks はブラウザーの保存範囲内で協調するための局所的な排他だ。送信済みの更新要求は、ページを閉じてもサーバーから消えるとは限らない。

## ブラウザーのロックは全端末を覆わない

リソース名を契約として定め、テナントや処理の識別情報を入れる。無関係な処理の競合と、同じ処理が別名を使う問題を避ける。[Web Locks 仕様](https://www.w3.org/TR/web-locks/)で API と実行条件を確認し、対象ブラウザーも検証する。埋め込み先のストレージ分割も協調範囲に影響する。

別のパソコンやブラウザーの実行は止められない。読み取りの重複は費用だけの問題かもしれないが、課金、通知、更新にはサーバーの冪等性や排他が必要だ。副作用を分類してから判断する。

## Promise の寿命が保持期間になる

例は `ifAvailable` で取得できなければ終了し、毎回のポーリングを待ち行列へ積まない。コールバックでは実際の処理を await する。待たずに Promise を開始して戻ると、処理中なのにロックが解放される。業務関数へキャンセルを渡し、通信、待機、ループも停止させる。

```javascript
export async function runAsLeader(locks, signal, work) {
  if (signal.aborted) throw signal.reason;
  return locks.request('report-refresh:v1', {
    mode: 'exclusive',
    ifAvailable: true,
  }, async lock => {
    if (!lock) return false;
    if (signal.aborted) throw signal.reason;
    await work(signal);
    return true;
  });
}

// Browser call site; work must stop when signal is aborted.
// await runAsLeader(navigator.locks, controller.signal, refreshReports);
```

即時判定モードなので、signal をロックの待機オプションとしては渡していない。協力しない `work` を強制停止することもできず、無視されれば Promise が終わるまで保持される。実用化には重複開始防止、失敗処理、待ち時間の制御も必要になる。

## 解放しても遠隔の更新は撤回されない

A が要求を送って停止し、B が引き継いで新しい値を書いた後、A の古い要求が届く場合がある。局所的な排他だけでは古い更新を見分けられない。書き込み版、比較交換、権威ある単調な fencing token が必要だ。

サーバーは同じ原子的処理の中でトークン比較と更新を行い、資格のない古い書き込みを拒否する。タブが別々に作った時刻値では権威ある連番にならない。同じ業務命令の再実行には冪等キーも使う。命令の同一性と、現在の書き込み資格は別の問題である。

## 通知は所有の証明ではない

BroadcastChannel は結果更新を知らせられるが、永続キューでも権限でもない。新しいタブは通知を逃すので保存済み状態を読む。受信側も版を確認して更新し、通知内容の任意の操作を直接実行しない。

待機、更新中、古い結果、再試行などを表示する。非表示になっただけで処理が永久に消えるとは限らず、復帰時は状態を再確認する。時間切れをごまかす強制取得は、古い処理を残して同時更新を増やし得る。

## 遅延を制御して引き継ぎを試す

同時開始、リーダー終了、例外、キャンセル、背景タブの復帰を検証する。サーバーでは A を遅らせ、B の完了後に A のトークンが拒否されることを確認する。二つ目のコールバックが走らないだけでは、通信後のデータ問題は検証できない。

まず報告の読み取りを協調し、その後で更新に必要なリース契約や版を決める。ロックは重複作業を減らし、サーバーの制約は共有データを守る。
