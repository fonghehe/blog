一个按钮有颜色和图标，不代表读屏用户知道它会做什么；文字在默认字号能显示，也不代表系统字体放大后还能完成支付。无障碍应该进入移动端功能验收，而不是发布前补一个标签。

## 从关键任务开始

挑选登录、查询、提交和错误恢复四条路径。检查读屏焦点顺序是否符合视觉阅读顺序，图标按钮是否有可理解的名称，开关与复选框是否读出当前状态。倒计时和异步成功提示需要恰当播报，但不能让每次列表刷新都打断用户阅读。

RN 中可利用 `accessibilityLabel`、角色和状态属性；Flutter 使用 `Semantics` 将复合控件表达为一个有意义的节点。两者都要避免把一整张卡片与卡片内部多个按钮重复读出。语义树应跟随用户任务设计，而不是机械复制视觉组件树。

## 字体与动态布局一起测

把系统字体调大后检查按钮是否仍可点击、金额与单位是否一起显示、错误提示是否被键盘挡住。不要靠固定高度把文本裁掉；必要时允许换行与页面滚动。测试深色模式、高对比度、横竖屏和外接键盘的基本路径。

自动检查能找出一部分缺失标签，最后仍需要在 iOS VoiceOver 和 Android TalkBack 上逐步完成真实任务。验收结果记录设备、系统版本、读屏模式和阻断点，便于回归。

## 用“转账确认”检查完整任务

把无障碍验收放到真实任务里：用户从收款人搜索进入确认页，核对姓名、金额和手续费，再决定提交。视觉上分开的金额与币种，读屏时应成为一个有意义的标签；“继续”按钮需要说明会进入确认步骤，而不是只读出图标名称。表单错误要同时关联具体字段，并在提交失败后让焦点到达错误摘要或首个错误，不能只用红色边框提示。

React Native 可用 `accessibilityRole`、`accessibilityLabel`、`accessibilityState` 与合理的元素分组表达语义；Flutter 则用 `Semantics`、`MergeSemantics` 和明确的焦点顺序。不要把整个页面粗暴合并成一个读屏节点，否则用户无法单独操作按钮。异步加载结束、弹窗打开与关闭时要检查焦点落点，避免停在已卸载的元素。动态字体放大后，金额、错误提示和主按钮都应可见，必要时允许布局换行而不是固定高度裁切。

| 场景 | 要检查的结果 |
| --- | --- |
| 读屏线性浏览 | 姓名、金额、费用、风险提示、确认按钮顺序合理 |
| 只用键盘或辅助开关 | 所有操作可达，焦点可见，不会困在弹窗 |
| 最大常用字体尺寸 | 文案可读，按钮不重叠，重要数字不截断 |
| 验证失败 | 错误被读出，返回输入框后内容仍保留 |

## 自动检查之外还要人工走查

先使用平台提供的检查工具发现缺失标签与对比度问题，再在 iOS VoiceOver 和 Android TalkBack 上实际完成上述转账流程。测试快速连点、网络慢时的状态播报，以及提交成功后焦点转移到结果标题。截图和静态检查无法证明读屏顺序与焦点恢复正确；记录设备、系统、字体设置和复现步骤，便于修复后复测。
