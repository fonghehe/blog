客服导出联系人，打开文件后发现备注成了公式，长编号还被转成科学计数法。服务端返回的字符串没有变，CSV 也能被解析，但用户看到的数据已经不是原来的语义。导出需要同时面对文件语法和表格软件的自动解释。

下面以含姓名、编号和备注的导出为例。代码选择对可疑文本拒绝 CSV 导出，并引导使用有明确单元格类型的格式。这是一项有取舍的产品策略，不是声称存在对所有表格软件都有效的万能转义。

## CSV 转义只解决行和列的边界

逗号、换行和双引号必须按 CSV 规则编码。将字段放进双引号，并把内部双引号写成两个，可以避免备注拆成新的列或行。CRLF 是常见的行分隔选择，读取方是否接受其他形式仍需约定。相关语法见 [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180)。

但是 `"=1+1"` 仍可能被表格软件当成公式。引号帮助 CSV 解析器划分单元格，并不声明“这是纯文本”。[OWASP 的公式注入说明](https://owasp.org/www-community/attacks/CSV_Injection)也提醒，保存后重新打开可能改变常见缓解措施的效果。因此安全验收不能止于第一次打开。

## 给导出列建立类型和使用场景

先区分编号、金额、自由文本与受控枚举。联系人编号即使全是数字，也可能需要保留前导零；金额是需要精度和币种的业务值，不能套用文本列的可疑字符规则，因为合法负数会以减号开头。业务专用导出比“任意对象转 CSV”更容易约束。

还要区分给人打开的报表与机器交换文件。给机器的文件可能必须精确保留原文；给表格软件的文件可能需要显式文本类型。一个按钮同时承担两种目标时，增加单引号之类的处理就会悄悄污染机器读取结果。把格式和目标写在按钮说明中，比藏在工具函数里更诚实。

## 示例采用拒绝策略，避免无声改写

以下只处理联系人文本列，遇到常见公式前缀或危险的前置控制字符就拒绝，而不是修改原值。这个规则可能拒绝合法姓名或备注，所以界面应说明原因，并提供使用文本单元格的工作簿导出。它没有覆盖所有软件、区域设置和再次保存行为；部署前仍要以目标软件测试。

```javascript
export function csvTextCell(value) {
  const text = String(value ?? '');
  if (/^[\s\uFEFF]*[=+\-@]/u.test(text) || /^[\t\r\n]/u.test(text)) {
    throw new Error('text requires a typed spreadsheet export');
  }
  return '"' + text.replaceAll('"', '""') + '"';
}

export function exportContacts(rows) {
  const header = ['id', 'name', 'note'].map(csvTextCell).join(',');
  return [header, ...rows.map(row =>
    [row.id, row.name, row.note].map(csvTextCell).join(',')
  )].join('\r\n') + '\r\n';
}
```

不要为了让导出成功而自动删除开头字符。原文可以包含真实的加号、换行和带负号的编号。若采用允许清单或加前缀政策，必须向用户说明会改变表示，并保证重导入时不会把变化误认为用户原始输入。类型化工作簿也要确认库实际写出的单元格类型，不能只看扩展名。

## 编码、权限与下载属于同一条链

UTF-8 BOM 可以帮助部分软件识别编码，但它不是公式防护，也不能保住所有编号格式。用中文、日文、双引号和换行样例在目标系统实测。列标题、枚举翻译和日期格式也要稳定，否则同一文件在人工查看与后续处理时会产生分歧。

导出接口应重新校验当前权限与筛选范围，不能因为页面已经加载过部分数据就放行全量导出。若生成过程较长，返回任务状态和受控下载地址，记录生成时的条件与列版本；不要在分析日志里复制完整备注来排查失败。

## 用往返样例验收，而不是只检查下载成功

固定测试普通文本、逗号、引号、嵌入换行、前导零编号、超长数字、公式前缀和前置控制字符。语法层做解析往返，应用层检查拒绝路径，目标表格软件里再验证首次打开以及保存后重开。

最后保留一份列契约：每列是什么类型、是否允许改写、面向哪种读取方。下一次添加“用户可编辑备注”时，这份契约会比一个通用 `escapeCsv` 函数更早提醒团队发现风险。
