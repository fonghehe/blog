“每周一纽约时间上午九点”与“每隔 168 小时执行一次”在跨越夏令时时并不等价。如果预约表单只把输入转成一个 UTC 字符串，第一次预约可能正确，下一次就提前或延后一小时。问题通常不在格式化函数，而在存储时丢掉了用户的日历意图。

预约、账单日和全天假期不能共用一个没有语义说明的 `timestamp` 字段。先区分需要保持当地钟表时间，还是需要保持时间线上的精确间隔，再谈组件和 API。

## 三类时间分别建模

已经发生的审计事件可以存一个明确时刻，例如带 `Z` 的 ISO 字符串。生日或全天假期是日历日期，不必强行转换成某个时区的午夜。未来的当地预约则至少需要当地日期时间和 IANA 时区标识；确认后还可记录解析出的时刻与偏移，便于解释当时的决定。

`UTC+8` 是固定偏移，不等于一套地区时区规则。地区规则可能调整，未来预约是否跟随新规则必须由业务决定。[Temporal 时区文档](https://tc39.es/proposal-temporal/docs/timezone.html)区分精确时间与钟表时间，并解释两者转换的歧义；这里采用这个区分，但不假设目标浏览器已经具备某个特定版本的 Temporal。

## 同一个当地时间可能出现两次

示例中的两个 UTC 时刻，在纽约都显示为 2026 年 11 月 1 日的 01:30。它们相差一小时，却会在省略偏移的界面中看起来完全相同。下面是只依赖 `Intl.DateTimeFormat` 的可运行验证。

```javascript
export function formatMeeting(instant, timeZone, locale = 'en-GB') {
  return new Intl.DateTimeFormat(locale, {
    timeZone,
    dateStyle: 'medium',
    timeStyle: 'short',
  }).format(new Date(instant));
}

const first = '2026-11-01T05:30:00Z';
const second = '2026-11-01T06:30:00Z';
const zone = 'America/New_York';
console.assert(formatMeeting(first, zone) === formatMeeting(second, zone));
console.assert(new Date(first).getTime() !== new Date(second).getTime());
```

预约确认页需要在重叠时间中给出选择，例如较早或较晚的一次，并显示对应偏移。春季调整时还存在根本没有发生的当地时间。把不存在的 02:30 静默挪到 03:30，会改变用户的预约；可以拒绝并要求重选，也可以提供明确的自动调整政策，但不能无声处理。

## 表单值不自动携带时区

`datetime-local` 表达当地日历值，不会替你确定地区时区。不要把它直接传给依赖机器本地配置的解析逻辑，然后假设所有用户都在同一地区。接口应接收明确字段，例如当地时间、时区和歧义处理方式，在统一的服务端规则下解析，再返回可确认的精确时刻。

服务端返回校验失败时，保留原始输入，让用户修改歧义选项。若用户从上海旅行到东京，既有纽约预约仍应保留纽约语义；展示时可以附带查看者当地时间，但不能覆盖预约所属时区。编辑页还要区分“更换显示时区”和“把会议改到另一个当地九点”。

## 重复计划应保存规则，不只保存下一次结果

按当地每周九点重复，需要保存星期、时分、地区时区及遇到缺口或重叠的政策。计算下一次时先推进日历，再按该时区解析，而不是把上次 UTC 值加七天毫秒。按精确间隔运行的监测任务则可以采用持续时间模型，两者不应该互相代替。

时区数据库升级后，未来实例可能变化。系统可以保存规则版本或解析记录，重新计算尚未发生的实例，并向受影响用户说明变化；已发生的审计事实不应跟着重新解释。若外部系统只支持 UTC，还要标记这是某次展开结果，不能据此推回完整重复规则。

## 边界测试比更多格式样例有用

测试重叠时间、缺失时间、跨年、半小时偏移地区、用户改变设备时区，以及客户端与服务端规则数据不同的情况。断言既包括解析出的时刻，也包括再次展示时用户看到的日期和钟表时间。全天事件则验证跨地区查看不会无故前移一天。

实际交付时，把“保持当地九点”还是“保持固定间隔”写进接口说明和产品文案。这样一次看似普通的预约修改，才不会在下次时钟调整时变成难以复现的数据问题。
