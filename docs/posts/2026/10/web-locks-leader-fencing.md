同一个报表页面开五个标签，就产生五组轮询。用 localStorage 写一个“我是主标签”的标记，看起来能降低请求数，但两个标签同时读取空值再写入时，都可能认为自己赢了。依靠时间戳超时接管，还会遇到后台冻结和系统时钟变化。

Web Locks 可以让同一浏览器存储范围内的上下文协作，但它解决的是局部互斥。标签一旦向服务端发出了写请求，关掉页面也不能保证那个请求从世界上消失。

## 锁的范围不是账户的所有设备

Web Locks 的资源名由应用约定。应把租户或任务身份纳入命名策略，避免不相关工作争抢同一把锁，也避免同一份工作使用不同名字。API 和权限、环境要求见 [Web Locks 规范](https://www.w3.org/TR/web-locks/)。目标浏览器需要单独验证，第三方上下文的存储隔离也会影响协作范围。

一个浏览器里的锁不能阻止另一台电脑或另一个浏览器提交相同任务。若任务只是读取报表，重复执行可能是成本问题；若会计费、发送通知或修改数据，就必须有服务端幂等或互斥约束。先按副作用分类，才能判断锁是否足够。

## Promise 的寿命就是持锁寿命

下面采用 `ifAvailable`：拿不到锁就返回，不把每次轮询都排成未来积压。回调必须等待真实工作完成；在内部启动一个未等待的 Promise 后立即返回，锁就会提前释放。取消信号传给业务函数，由业务函数终止 Fetch、定时等待和循环。

```javascript
export async function runAsLeader(locks, signal, work) {
  if (signal.aborted) throw signal.reason;
  return locks.request('report-refresh:v1', {
    mode: 'exclusive',
    ifAvailable: true,
  }, async lock => {
    if (!lock) return false;
    if (signal.aborted) throw signal.reason;
    await work(signal);
    return true;
  });
}

// Browser call site; work must stop when signal is aborted.
// await runAsLeader(navigator.locks, controller.signal, refreshReports);
```

示例没有把信号传进锁选项，因为 `ifAvailable` 不是等待队列模式。它也不能强行中断一个不配合的 `work`。如果任务忽略信号，持锁时间仍会持续到 Promise 完成。生产实现还要防止重复启动、捕获失败并制定退避，不应让多个定时器在同一标签内不断竞争。

## 本地释放不代表远端写入停止

设主标签 A 发出更新后被挂起，标签 B 接管并提交新结果。A 的旧请求可能晚到，覆盖 B 的更新。客户端互斥无法替服务端判断哪个结果已经过期。需要写入版本、比较并交换，或者由服务端签发单调递增的栅栏令牌。

采用栅栏时，服务端在同一原子事务中比较令牌和更新资源，只接受符合规则的新持有者写入。令牌不能由各标签自己生成一个时间戳假装单调；它应来自权威协调点。对于同一业务命令的重复执行，再配合幂等键；幂等键与栅栏分别回答“是不是同一命令”和“是不是仍有写入资格”。

## 广播是通知，不是锁的证明

BroadcastChannel 可以通知其他标签“有新结果”，但消息不是持久队列，也不是授权依据。新标签可能错过广播，所以打开时应读取持久状态。收到消息后还要按资源版本决定是否刷新，不能直接执行任意消息携带的操作。

主标签状态也应面向用户可解释：等待中、正在刷新、结果过期、失败重试。页面隐藏不等于任务被永久终止，恢复时重新验证状态。不要用强制抢锁掩盖超时，否则旧工作仍可能运行，问题只会从重复读取升级为并发写入。

## 用可控的暂停重现接管顺序

测试两个标签同时开始、主标签关闭、工作抛错、主动取消和恢复后台标签。服务端测试要专门延迟 A 的请求，让 B 先完成，再验证 A 的旧令牌被拒绝。这里只测“第二个回调没运行”不够，因为真正的数据风险在跨越浏览器边界之后。

先把报表读取协调做好，再决定哪些写操作需要权威租约与版本检查。锁节省的是重复工作，服务端约束保护的才是共享数据的正确性。
