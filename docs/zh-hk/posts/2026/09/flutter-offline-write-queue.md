離線優先不等於「失敗後一直重試」。用戶在港鐵上編輯一張工單，應用重啟後仍應看見自己的修改；恢復網絡時，同一操作不能提交兩次；如果另一台設備已修改工單，還要給用戶一個可理解的衝突狀態。

## 把本地記錄當作主視圖

UI 先從本地數據庫讀取，寫入時在一個交易中同時更新可見記錄和待同步隊列。隊列項至少保存 `operationId`、實體 ID、基礎版本、變更內容、建立時間及狀態。`operationId` 也發給伺服器作為冪等鍵；超時後的重試才不會生成重複工單。

```text
用戶編輯 → 本地交易寫入草稿 + pending 操作 → UI 顯示「待同步」
網絡可用 → 按實體串行提交 → 伺服器確認版本 → 本地標記 synced
版本衝突 → 標記 conflict → 提供查看差異 / 重新提交入口
```

隊列要允許單項失敗，不能因為第一條格式錯誤就堵住所有工單。網絡錯誤退避重試；權限失效暫停並等待重新登入；伺服器明確拒絕時保留本地草稿並展示可操作原因。

## 衝突策略按欄位決定

備註可以考慮追加式合併，金額和審批結果通常需要伺服器裁決，不應使用「最後寫入覆蓋」。同步完成後用伺服器返回的最終實體替換本地快照，並清理已經確認的操作。後台任務在移動系統中不保證持續運行，因此前台恢復和用戶主動同步都應能推進隊列。

測試時覆蓋強制關閉應用後恢復、重複回執、兩台設備同時編輯和權限過期。只測斷網期間能顯示草稿，無法證明同步安全。
