一個按鈕有顏色和圖示，不代表屏幕閱讀器用戶知道它會做什麼；文字在預設字號能顯示，也不代表系統字體放大後還能完成支付。無障礙應該進入移動端功能驗收，而不是發佈前補一個標籤。

## 從關鍵任務開始

挑選登入、查詢、提交和錯誤恢復四條路徑。檢查屏幕閱讀器焦點順序是否符合視覺閱讀順序，圖示按鈕是否有可理解的名稱，開關與復選框是否讀出當前狀態。倒計時和非同步成功提示需要恰當播報，但不能讓每次列表刷新都打斷用戶閱讀。

RN 中可利用 `accessibilityLabel`、角色和狀態屬性；Flutter 使用 `Semantics` 將復合控件表達為一個有意義的節點。兩者都要避免把一整張卡片與卡片內部多個按鈕重複讀出。語義樹應跟隨用戶任務設計，而不是機械複製視覺組件樹。

## 字體與動態佈局一起測

把系統字體調大後檢查按鈕是否仍可點擊、金額與單位是否一起顯示、錯誤提示是否被鍵盤擋住。不要靠固定高度把文字裁掉；必要時允許換行與頁面滾動。測試深色模式、高對比度、橫竪屏和外接鍵盤的基本路徑。

自動檢查能找出一部分缺失標籤，最後仍需要在 iOS VoiceOver 和 Android TalkBack 上逐步完成真實任務。驗收結果記錄設備、系統版本、屏幕閱讀器模式和阻斷點，便於回歸。

## 用“轉賬確認”檢查完整任務

把無障礙驗收放到真實任務里：用戶從收款人搜索進入確認頁，核對姓名、金額和手續費，再決定提交。視覺上分開的金額與幣種，讀屏時應成為一個有意義的標籤；“繼續”按鈕需要說明會進入確認步驟，而不是只讀出圖標名稱。表單錯誤要同時關聯具體字段，並在提交失敗後讓焦點到達錯誤摘要或首個錯誤，不能只用紅色邊框提示。

React Native 可用 `accessibilityRole`、`accessibilityLabel`、`accessibilityState` 與合理的元素分組表達語義；Flutter 則用 `Semantics`、`MergeSemantics` 和明確的焦點順序。不要把整個頁面粗暴合併成一個讀屏節點，否則用戶無法單獨操作按鈕。異步加載結束、彈窗打開與關閉時要檢查焦點落點，避免停在已卸載的元素。動態字體放大後，金額、錯誤提示和主按鈕都應可見，必要時允許佈局換行而不是固定高度裁切。

| 場景 | 要檢查的結果 |
| --- | --- |
| 讀屏線性瀏覽 | 姓名、金額、費用、風險提示、確認按鈕順序合理 |
| 只用鍵盤或輔助開關 | 所有操作可達，焦點可見，不會困在彈窗 |
| 最大常用字體尺寸 | 文案可讀，按鈕不重疊，重要數字不截斷 |
| 驗證失敗 | 錯誤被讀出，返回輸入框後內容仍保留 |

## 自動檢查之外還要人工走查

先使用平台提供的檢查工具發現缺失標籤與對比度問題，再在 iOS VoiceOver 和 Android TalkBack 上實際完成上述轉賬流程。測試快速連點、網絡慢時的狀態播報，以及提交成功後焦點轉移到結果標題。截圖和靜態檢查無法證明讀屏順序與焦點恢復正確；記錄設備、系統、字體設置和復現步驟，便於修復後復測。
