“每週一紐約時間上午九點”與“每隔 168 小時執行一次”在跨越夏令時時並不等價。如果預約表單只把輸入轉成一個 UTC 字符串，第一次預約可能正確，下一次就提前或延後一小時。問題通常不在格式化函數，而在存儲時丟掉了用戶的日曆意圖。

預約、賬單日和全天假期不能共用一個沒有語義說明的 `timestamp` 字段。先區分需要保持當地鐘錶時間，還是需要保持時間線上的精確間隔，再談組件和 API。

## 三類時間分別建模

已經發生的審計事件可以存一個明確時刻，例如帶 `Z` 的 ISO 字符串。生日或全天假期是日曆日期，不必強行轉換成某個時區的午夜。未來的當地預約則至少需要當地日期時間和 IANA 時區標識；確認後還可記錄解析出的時刻與偏移，便於解釋當時的決定。

`UTC+8` 是固定偏移，不等於一套地區時區規則。地區規則可能調整，未來預約是否跟隨新規則必須由業務決定。[Temporal 時區文檔](https://tc39.es/proposal-temporal/docs/timezone.html)區分精確時間與鐘錶時間，並解釋兩者轉換的歧義；這裡採用這個區分，但不假設目標瀏覽器已經具備某個特定版本的 Temporal。

## 同一個當地時間可能出現兩次

示例中的兩個 UTC 時刻，在紐約都顯示為 2026 年 11 月 1 日的 01:30。它們相差一小時，卻會在省略偏移的界面中看起來完全相同。下面是只依賴 `Intl.DateTimeFormat` 的可運行驗證。

```javascript
export function formatMeeting(instant, timeZone, locale = 'en-GB') {
  return new Intl.DateTimeFormat(locale, {
    timeZone,
    dateStyle: 'medium',
    timeStyle: 'short',
  }).format(new Date(instant));
}

const first = '2026-11-01T05:30:00Z';
const second = '2026-11-01T06:30:00Z';
const zone = 'America/New_York';
console.assert(formatMeeting(first, zone) === formatMeeting(second, zone));
console.assert(new Date(first).getTime() !== new Date(second).getTime());
```

預約確認頁需要在重疊時間中給出選擇，例如較早或較晚的一次，並顯示對應偏移。春季調整時還存在根本沒有發生的當地時間。把不存在的 02:30 靜默挪到 03:30，會改變用戶的預約；可以拒絕並要求重選，也可以提供明確的自動調整政策，但不能無聲處理。

## 表單值不自動攜帶時區

`datetime-local` 表達當地日曆值，不會替你確定地區時區。不要把它直接傳給依賴機器本地配置的解析邏輯，然後假設所有用戶都在同一地區。接口應接收明確字段，例如當地時間、時區和歧義處理方式，在統一的服務端規則下解析，再返回可確認的精確時刻。

服務端返回校驗失敗時，保留原始輸入，讓用戶修改歧義選項。若用戶從上海旅行到東京，既有紐約預約仍應保留紐約語義；展示時可以附帶查看者當地時間，但不能覆蓋預約所屬時區。編輯頁還要區分“更換顯示時區”和“把會議改到另一個當地九點”。

## 重複計劃應保存規則，不只保存下一次結果

按當地每週九點重複，需要保存星期、時分、地區時區及遇到缺口或重疊的政策。計算下一次時先推進日曆，再按該時區解析，而不是把上次 UTC 值加七天毫秒。按精確間隔運行的監測任務則可以採用持續時間模型，兩者不應該互相代替。

時區數據庫升級後，未來實例可能變化。系統可以保存規則版本或解析記錄，重新計算尚未發生的實例，並向受影響用戶說明變化；已發生的審計事實不應跟著重新解釋。若外部系統只支持 UTC，還要標記這是某次展開結果，不能據此推回完整重複規則。

## 邊界測試比更多格式樣例有用

測試重疊時間、缺失時間、跨年、半小時偏移地區、用戶改變設備時區，以及客戶端與服務端規則數據不同的情況。斷言既包括解析出的時刻，也包括再次展示時用戶看到的日期和鐘錶時間。全天事件則驗證跨地區查看不會無故前移一天。

實際交付時，把“保持當地九點”還是“保持固定間隔”寫進接口說明和產品文案。這樣一次看似普通的預約修改，才不會在下次時鐘調整時變成難以復現的數據問題。
