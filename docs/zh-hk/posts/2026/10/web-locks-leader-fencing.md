同一個報表頁面開五個標籤，就產生五組輪詢。用 localStorage 寫一個“我是主標籤”的標記，看起來能降低請求數，但兩個標籤同時讀取空值再寫入時，都可能認為自己贏了。依靠時間戳超時接管，還會遇到後台凍結和系統時鐘變化。

Web Locks 可以讓同一瀏覽器存儲範圍內的上下文協作，但它解決的是局部互斥。標籤一旦向服務端發出了寫請求，關掉頁面也不能保證那個請求從世界上消失。

## 鎖的範圍不是賬戶的所有設備

Web Locks 的資源名由應用約定。應把租戶或任務身份納入命名策略，避免不相關工作爭搶同一把鎖，也避免同一份工作使用不同名字。API 和權限、環境要求見 [Web Locks 規範](https://www.w3.org/TR/web-locks/)。目標瀏覽器需要單獨驗證，第三方上下文的存儲隔離也會影響協作範圍。

一個瀏覽器里的鎖不能阻止另一台電腦或另一個瀏覽器提交相同任務。若任務只是讀取報表，重複執行可能是成本問題；若會計費、發送通知或修改數據，就必須有服務端冪等或互斥約束。先按副作用分類，才能判斷鎖是否足夠。

## Promise 的壽命就是持鎖壽命

下面採用 `ifAvailable`：拿不到鎖就返回，不把每次輪詢都排成未來積壓。回調必須等待真實工作完成；在內部啓動一個未等待的 Promise 後立即返回，鎖就會提前釋放。取消信號傳給業務函數，由業務函數終止 Fetch、定時等待和循環。

```javascript
export async function runAsLeader(locks, signal, work) {
  if (signal.aborted) throw signal.reason;
  return locks.request('report-refresh:v1', {
    mode: 'exclusive',
    ifAvailable: true,
  }, async lock => {
    if (!lock) return false;
    if (signal.aborted) throw signal.reason;
    await work(signal);
    return true;
  });
}

// Browser call site; work must stop when signal is aborted.
// await runAsLeader(navigator.locks, controller.signal, refreshReports);
```

示例沒有把信號傳進鎖選項，因為 `ifAvailable` 不是等待隊列模式。它也不能強行中斷一個不配合的 `work`。如果任務忽略信號，持鎖時間仍會持續到 Promise 完成。生產實現還要防止重複啓動、捕獲失敗並制定退避，不應讓多個定時器在同一標籤內不斷競爭。

## 本地釋放不代表遠端寫入停止

設主標籤 A 發出更新後被掛起，標籤 B 接管並提交新結果。A 的舊請求可能晚到，覆蓋 B 的更新。客戶端互斥無法替服務端判斷哪個結果已經過期。需要寫入版本、比較並交換，或者由服務端簽發單調遞增的柵欄令牌。

採用柵欄時，服務端在同一原子事務中比較令牌和更新資源，只接受符合規則的新持有者寫入。令牌不能由各標籤自己生成一個時間戳假裝單調；它應來自權威協調點。對於同一業務命令的重複執行，再配合冪等鍵；冪等鍵與柵欄分別回答“是不是同一命令”和“是不是仍有寫入資格”。

## 廣播是通知，不是鎖的證明

BroadcastChannel 可以通知其他標籤“有新結果”，但消息不是持久隊列，也不是授權依據。新標籤可能錯過廣播，所以打開時應讀取持久狀態。收到消息後還要按資源版本決定是否刷新，不能直接執行任意消息攜帶的操作。

主標籤狀態也應面向用戶可解釋：等待中、正在刷新、結果過期、失敗重試。頁面隱藏不等於任務被永久終止，恢復時重新驗證狀態。不要用強制搶鎖掩蓋超時，否則舊工作仍可能運行，問題只會從重複讀取升級為併發寫入。

## 用可控的暫停重現接管順序

測試兩個標籤同時開始、主標籤關閉、工作拋錯、主動取消和恢復後台標籤。服務端測試要專門延遲 A 的請求，讓 B 先完成，再驗證 A 的舊令牌被拒絕。這裡只測“第二個回調沒運行”不夠，因為真正的數據風險在跨越瀏覽器邊界之後。

先把報表讀取協調做好，再決定哪些寫操作需要權威租約與版本檢查。鎖節省的是重複工作，服務端約束保護的才是共享數據的正確性。
