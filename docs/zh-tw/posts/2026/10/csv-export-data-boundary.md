客服導出聯繫人，打開檔案後發現備注成了公式，長編號還被轉成科學計數法。伺服器端返回的字串沒有變，CSV 也能被解析，但使用者看到的資料已經不是原來的語義。導出需要同時面對檔案語法和表格軟體的自動解釋。

下面以含姓名、編號和備注的導出為例。程式碼選擇對可疑文本拒絕 CSV 導出，並引導使用有明確單元格類型的格式。這是一項有取捨的產品策略，不是聲稱存在對所有表格軟體都有效的萬能轉義。

## CSV 轉義只解決行和列的邊界

逗號、換行和雙引號必須按 CSV 規則編碼。將欄位放進雙引號，並把內部雙引號寫成兩個，可以避免備注拆成新的列或行。CRLF 是常見的行分隔選擇，讀取方是否接受其他形式仍需約定。相關語法見 [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180)。

但是 `"=1+1"` 仍可能被表格軟體當成公式。引號幫助 CSV 解析器劃分單元格，並不聲明“這是純文本”。[OWASP 的公式注入說明](https://owasp.org/www-community/attacks/CSV_Injection)也提醒，保存後重新打開可能改變常見緩解措施的效果。因此安全驗收不能止於第一次打開。

## 給導出列建立類型和使用場景

先區分編號、金額、自由文本與受控枚舉。聯繫人編號即使全是數字，也可能需要保留前導零；金額是需要精度和幣種的業務值，不能套用文本列的可疑字符規則，因為合法負數會以減號開頭。業務專用導出比“任意對象轉 CSV”更容易約束。

還要區分給人打開的報表與機器交換檔案。給機器的檔案可能必須精確保留原文；給表格軟體的檔案可能需要顯式文本類型。一個按鈕同時承擔兩種目標時，增加單引號之類的處理就會悄悄污染機器讀取結果。把格式和目標寫在按鈕說明中，比藏在工具函數里更誠實。

## 示例採用拒絕策略，避免無聲改寫

以下只處理聯繫人文本列，遇到常見公式前綴或危險的前置控制字符就拒絕，而不是修改原值。這個規則可能拒絕合法姓名或備注，所以界面應說明原因，並提供使用文本單元格的工作簿導出。它沒有覆蓋所有軟體、區域設置和再次保存行為；部署前仍要以目標軟體測試。

```javascript
export function csvTextCell(value) {
  const text = String(value ?? '');
  if (/^[\s\uFEFF]*[=+\-@]/u.test(text) || /^[\t\r\n]/u.test(text)) {
    throw new Error('text requires a typed spreadsheet export');
  }
  return '"' + text.replaceAll('"', '""') + '"';
}

export function exportContacts(rows) {
  const header = ['id', 'name', 'note'].map(csvTextCell).join(',');
  return [header, ...rows.map(row =>
    [row.id, row.name, row.note].map(csvTextCell).join(',')
  )].join('\r\n') + '\r\n';
}
```

不要為了讓導出成功而自動刪除開頭字符。原文可以包含真實的加號、換行和帶負號的編號。若採用允許清單或加前綴政策，必須向使用者說明會改變表示，並保證重導入時不會把變化誤認為使用者原始輸入。類型化工作簿也要確認庫實際寫出的單元格類型，不能只看擴展名。

## 編碼、權限與下載屬於同一條鏈

UTF-8 BOM 可以幫助部分軟體識別編碼，但它不是公式防護，也不能保住所有編號格式。用中文、日文、雙引號和換行樣例在目標系統實測。列標題、枚舉翻譯和日期格式也要穩定，否則同一檔案在人工查看與後續處理時會產生分歧。

導出介面應重新校驗當前權限與篩選範圍，不能因為頁面已經載入過部分資料就放行全量導出。若生成過程較長，返回任務狀態和受控下載地址，記錄生成時的條件與列版本；不要在分析紀錄里複製完整備注來排查失敗。

## 用往返樣例驗收，而不是只檢查下載成功

固定測試普通文本、逗號、引號、嵌入換行、前導零編號、超長數字、公式前綴和前置控制字符。語法層做解析往返，應用層檢查拒絕路徑，目標表格軟體里再驗證首次打開以及保存後重開。

最後保留一份列契約：每列是什麼類型、是否允許改寫、面向哪種讀取方。下一次添加“使用者可編輯備注”時，這份契約會比一個通用 `escapeCsv` 函數更早提醒團隊發現風險。
